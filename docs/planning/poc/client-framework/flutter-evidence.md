# Flutter / sing-box client route: official evidence

Evidence checked 2026-10-08. This is a bounded evidence inventory, not a framework, engine, or platform-support decision. “Documented fact” describes the cited source; “inference” is a scoped consequence; “unknown” means no target build or runtime qualification was performed. The historical unified-client analysis remains proposal material. The current Linux systemd installer is not evidence for a Flutter GUI or other operating systems.

| Fixed row | Evidence and boundary |
|---|---|
| Platform and architecture coverage | **Documented fact:** Flutter’s [supported-platforms matrix](https://docs.flutter.dev/reference/supported-platforms), as of Flutter 3.47, lists Android x64/Arm32/Arm64 (API 24–37), iOS Arm64 (15–27), Windows x64/Arm64 (10/11), macOS x64/Arm64 (12–27), Debian x64/Arm64 (10–13), and Ubuntu x64/Arm64 (20.04–24.04 LTS); the page distinguishes supported, CI-tested, and unsupported combinations and says macOS x64 is being phased out. These are Flutter deployment claims only. **Unknown:** EasyNet engine/client support, Android TV, packaging, and tested minimum targets/architectures. No Flutter version pin is selected. |
| Go service, Flutter bridge, libbox packaging | **Documented fact:** Flutter documents platform channels for asynchronous messages between Dart UI and host Kotlin/Java, Swift/Objective-C, C++, or C code ([platform channels](https://docs.flutter.dev/platform-integration/platform-channels)); Flutter separately documents Dart FFI and native-library build/bundling ([FFI](https://docs.flutter.dev/platform-integration/bind-native-code)). The official sing-box [`cmd/internal/build_libbox/main.go`](https://raw.githubusercontent.com/SagerNet/sing-box/testing/cmd/internal/build_libbox/main.go) on the `testing` branch invokes `gomobile bind` on `experimental/libbox`: its Android path names `libbox.aar` (API 24) and `libbox-legacy.aar` (API 21), while its Apple path names iOS, iOS Simulator, tvOS, tvOS Simulator, and macOS targets, with iOS 15.0/macOS 13.0/tvOS 17.0 minimum flags and `Libbox.xcframework` output. These are checked-in build-script declarations, not executed build results. **Inference:** the inspected Apple path declares macOS 13 even though Flutter UI lists macOS 12; a combined candidate must meet all component requirements, and no minimum target is qualified. **Inference:** channel/FFI and libbox artifacts could be integration inputs, not evidence of an existing Go-service or EasyNet integration. **Unknown:** IPC contract, bridge maintenance, actual API/ABI compatibility, produced artifacts, EasyNet packaging, and lifecycle. The official [sing-box repository](https://github.com/SagerNet/sing-box) identifies the project and its GPL-3.0-or-later license. |
| Apple Network Extension, process, entitlement, signing | **Documented fact:** Apple’s [packet tunnel provider class](https://developer.apple.com/documentation/networkextension/nepackettunnelprovider) describes a principal class for a packet-tunnel-provider app extension; its [deployment technote](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment) gives platform packaging/minimum-OS rows and distinguishes app-extension user context from system-extension global context. For macOS packet tunnels it lists app extensions as App Store only and system extensions from macOS 10.15 without that restriction; Developer ID direct distribution applies to eligible rows, not every packaging form. Apple’s [Network Extensions entitlement page](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.networkextension) lists the packet-tunnel entitlement and the macOS outside-App-Store provisioning-profile and signing steps. The cited pages were read via official documentation search content; the JS HTML/Markdown endpoint was not directly readable. **Inference:** this native VPN capability is a separate concern from Flutter UI support. **Unknown:** whether a proposed client needs this provider, entitlement availability for this product/team, selected packaging/OS target, signing, and store/distribution acceptance. No entitlement approval is inferred from an app UI or a WireGuard endpoint. |
| Android VpnService consent and lifecycle | **Documented fact:** Android’s [VPN guide](https://developer.android.com/develop/connectivity/vpn) requires calling `VpnService.prepare()` to obtain user approval when needed, then describes protecting the tunnel socket, establishing a TUN interface, and service lifecycle responsibilities. **Inference:** Flutter UI alone does not satisfy this native service/consent path. **Unknown:** EasyNet service implementation, foreground behavior, process recovery, target API behavior, and device qualification. |
| Desktop TUN and privilege boundary | **Documented fact:** Flutter’s target matrix documents desktop UI deployment; Apple’s deployment technote documents separate native packet-tunnel provider packaging (links above). **Inference:** desktop UI support does not itself establish TUN creation or privilege/integration support. **Unknown:** Linux/Windows/macOS TUN API, privilege model, installer/user-consent flow, supported architecture, and real-client operation. No generic “desktop TUN works” claim is made. |
| License, dependencies, release gates | **Documented fact:** sing-box’s [official repository](https://github.com/SagerNet/sing-box) states GPL-3.0-or-later and includes an additional no-derivative-name/association clause. Flutter’s official [native FFI documentation](https://docs.flutter.dev/platform-integration/bind-native-code) documents a native build hook and automatic bundling. **Inference:** a candidate release needs dependency/source inventory, notices, reproducible per-target artifacts, update ownership, and distribution review. **Unknown:** EasyNet’s intended distribution model, complete transitive license obligations, compatibility/support policy, signing credentials, and release gates. This is a factual engineering gate, not legal advice or a legal conclusion. |
| Native four-protocol and format bounds | **Documented fact:** the frozen [capability matrix](../../capability-matrix.md) names EasyNet’s four native server modules as Xray+Reality, Hysteria2, Shadowsocks 2022, and AmneziaWG; the wireguard-named module is AWG. Official [sing-box outbound docs](https://sing-box.sagernet.org/configuration/outbound/) list generic Shadowsocks, Hysteria2, and WireGuard types; they do not establish EasyNet’s Shadowsocks 2022 format or AmneziaWG obfuscation support. The [AmneziaWG specification](https://docs.amnezia.org/documentation/amnezia-wg/) documents AWG-specific obfuscation fields beyond standard WireGuard. Project X documents [REALITY](https://xtls.github.io/en/config/transports/reality.html) as Xray configuration. **Inference:** protocol-name overlap or a WireGuard endpoint cannot establish native AWG or Xray+Reality compatibility. **Unknown:** exact format import/export, client-side support for all four existing protocols, and libbox parity. Do not silently drop a native protocol or infer AWG from WireGuard. |

## Bounded future host PoC prerequisites (not run)

After a framework/engine decision and frozen protocol/API contracts, define one host per proposed OS/architecture and record exact minimum OS, SDK/toolchain, build artifact, UI-to-service IPC, TUN/VPN integration, permission/entitlement/signing state, and one connection/config-format acceptance case. Obtain the needed device, signing identity, and user consent before any live VPN test. Record unsupported combinations as unknown until built and exercised. This plan does not select an engine or authorize a live VPN, signing, store submission, or release.
