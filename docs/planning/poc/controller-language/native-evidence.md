# Native candidate evidence: Swift service with system OpenSSH

Snapshot date: 2026-10-07. Evidence is from official Apple, Swift.org and
OpenBSD manual sources available on that date. Root captured local environment
facts read-only: macOS OpenSSH_10.3p1 LibreSSL 3.3.6, Swift 6.4 targeting
arm64-apple-macosx27.0.0, and arm64 host. These facts do not certify target
runtime behavior or packaged-app acceptance. No install, build, SSH connection,
key use, Keychain access, runtime test, or language/framework selection occurred.

| Dimension | Documented evidence | Unknown / implication |
|---|---|---|
| Swift/runtime | Swift.org announced Swift 6.4 on 2026-09-15; Swift.org says Swift is Apache License 2.0. Foundation `Process` runs an executable with argument array; this avoids shell parsing when directly launching `/usr/bin/ssh`. | Root captured Swift 6.4 and its target above; exact Xcode/macOS version and app deployment target remain unmeasured. `Process` does not itself constrain OpenSSH config, environment, inherited file descriptors, prompts, or outputs. Full dependency/license inventory and release/support policy for the eventual product remain to assess. |
| SSH auth and host trust | Local read-only version capture reports `/usr/bin/ssh` as OpenSSH_10.3p1 LibreSSL 3.3.6. OpenBSD-current `ssh_config(5)` documents `IdentityFile`, `IdentitiesOnly`, `BatchMode`, `UserKnownHostsFile`, `StrictHostKeyChecking`, `ConnectTimeout` and `ServerAlive*`. Explicit identity plus `IdentitiesOnly yes` constrains offered identities; BatchMode disables interactive prompts. `StrictHostKeyChecking yes` refuses unknown and changed host keys; `accept-new` auto-adds first-use keys and therefore does not meet explicit trust enrollment by itself. | OpenBSD-current documentation is a capability reference, not proof that all described semantics/defaults match Apple's build. First-use fingerprint assurance/recording, changed-key refusal, target/endpoint binding, config-file isolation, agent/keychain behavior, safe command construction and credential resolution need an ADR-003 implementation and tests. No SSH activity occurred. |
| Local cancel vs remote outcome | Apple Foundation `Process.terminate()` sends SIGTERM to the local task and subtasks, and Apple says termination may fail if ignored. `terminationHandler` runs when the local task completes; status describes that process. | Stopping the local `ssh` process or seeing its exit does not establish whether a remote command started, stopped, succeeded, or failed. Reconcile uncertain operations and preserve ownership per ADR-001/003; no remote completion/cancel proof comes from Process. No server support/effect claim. |
| Secrets / Keychain | Apple TN3137 (republished 2022-11-01) distinguishes file-based and data-protection macOS keychains. `SecItem` defaults to file-based unless `kSecUseDataProtectionKeychain` or synchronizable behavior is requested; their access-control models differ (file-based ACLs versus data-protection access groups/optional `SecAccessControl`). Apple's `kSecAttrAccessible` docs say macOS requires data-protection or synchronizable mode to use this attribute; `ThisDeviceOnly` cannot sync. Apple's general accessibility guide describes `WhenUnlocked` as default only when no accessibility setting is specified, while TN3137 shows why the actual macOS backend must be identified first. Apple says `ThisDeviceOnly` items do not migrate to a different device's backup. `kSecUseAuthenticationUI` controls prompting; `kSecUseAuthenticationUIFail` is deprecated in favor of `LAContext.interactionNotAllowed`, which can return `errSecInteractionNotAllowed`. | Prompt/locked-store behavior, ACL identity after signing/updates, app-versus-CLI access groups and entitlements, user-context requirement for data-protection keychain, rotation, recovery/export and backup policy depend on the chosen backend/item attributes and need a reviewed implementation. Keychain is macOS-specific; no cross-platform equivalent is implied. Nothing was accessed or tested. |
| JSON contract strictness | Foundation `JSONDecoder` decodes `Decodable` types and exposes key conversion strategies. Synthesized typed decoding can read declared keys; custom `Decodable` can inspect keys. | The public decoder API does not expose a strict unknown-member or duplicate-name rejection mode. Unknown-field behavior for custom decoders and duplicate-name behavior need tests against the contract; do not treat Codable decoding as proof of strict serialization. Exact numbers, canonical bytes and compatibility also remain unverified. |
| macOS arm64 packaging | Apple says Xcode 12.2+ includes arm64 in standard macOS architectures; standard Release settings can produce universal arm64+x86_64 binaries. Apple documents Developer ID signing and notarization for direct distribution, with hardened runtime and valid signatures among requirements. | No archive, signing, notarization, Gatekeeper, installer/update, reproducibility, universal dependency, or Apple Silicon runtime test was performed. System OpenSSH path/version and behavior under app sandbox/hardened runtime need target testing. |
| Portability and maintenance | Swift.org platform support page lists macOS deployment from 13.0 and development/deployment targets for macOS, Linux distributions and Windows. Swift 6.4 release notes describe Foundation and Subprocess cross-platform improvements. | The proposed Security/Keychain APIs and `/usr/bin/ssh` process are macOS-specific; portable Swift source does not make those facilities portable. Linux/Windows need separate SSH and secret-store implementations plus parity/security tests. OS-provided OpenSSH maintenance/version cadence and dependency closure are not measured. |

Positive evidence: Swift provides a shared service language/runtime, Apple Keychain
APIs and a local OpenSSH process boundary; OpenSSH exposes strict host-key and
identity controls; Apple supports arm64 and notarized distribution. Negative
boundary: local process state is not remote outcome, and this evidence does not
implement ADR-001 shared policy or ADR-003 trust/cancel requirements.
