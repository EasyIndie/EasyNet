# 每卡模型路由与成本校准

日期：2026-10-06；使用记录审计补充于 [2026-10-08 审计](model-usage-audit-2026-10-08.md)。逐卡分配在 [任务卡索引](task-cards/README.md) 和每张卡的模型段。
用户已授权按本规范使用子 Agent：实际派发模型与推理档位记录在 task-result 中。
主聊天模型不会因此切换；尚未完成模型质量/总成本 benchmark。

## 分档与具体建议

| 档位 | 模型类型及当前示例 | 推理档位 | 适合内容 | 升级处理 |
|---|---|---|---|---|
| D | 高效率小模型，例如 Luna | low | 导航/指引核对、既有事实提取、检查报告 | 歧义或跨文档冲突交 Sol |
| C | 小型编码模型，例如 Luna | medium | 已冻结接口的单函数、fixture、数据规则、单页面 | 两次失败或接口变化交 Sol |
| I | 中档推理编码模型，例如 GPT-6.1 Sol | medium | SSH/vault/platform adapter、状态恢复、跨边界集成 | 关键安全边界用 Sol high；复杂争议再 Astra |
| R | 更强设计/审查模型，例如 GPT-6.1 Sol | high | ADR 决策、trust/加密/权限/销毁审查、阶段 Gate | 维护者接受决策与验收；模型不是资源操作授权来源 |

名称是当前官方角色示例，不是固定版本、账号可用性或单次价格承诺。实际运行时选择界面可用
的同档模型；若使用其他厂商，同样按本地任务评测映射。默认 D 用 Luna low、C 用 Luna medium、
I 用 Sol medium、R 用 Sol high；Astra 仅用于复杂争议。不要把最便宜的型号直接用于无冻结
接口的架构或密钥设计。高档不是自动正确，仍需运行测试并审查证据。

分配是本项目的风险判断：各卡综合接口歧义、需要跨模块阅读程度、平台知识和失败影响。
同一工作包的 fixture 卡可用 C，审查卡可用 R；不是把整个工作包都交给昂贵模型。
即使 C 卡修改了敏感代码，信任/加密/权限边界仍须强评审，不因执行模型便宜而省略。

[OpenAI 官方模型选择](https://developers.openai.com/api/docs/guides/model-selection)把 Luna
用于范围明确的任务，Sol 用于复杂技术工作，Astra 用于高要求分析，并建议用相同输入比较
模型和推理设置。本项目据此提出上述初始路由，未以官方角色说明替代项目准确率评测。
[官方推理指导](https://developers.openai.com/api/docs/guides/reasoning)说明较低推理强度通常使用较少 token；这不保证订阅费用下降或单任务质量不变。官方优化指导强调持续测量
与调整；本清单的档位是待校准建议，没有声称节省某个百分比。

## Ready 卡如何选择模型

先看卡内 `model.tier` 和 `review`，再确认所有前置 verified、接口版本/路径/命令已经绑定。
D/C 只收到短 AGENTS + 单卡 + 列出的局部输入 + 已接受合同，避免 56 工作包/全量 JSON 入上下文。
I/R 用依赖的事实摘要、失败复现和小范围 diff，不重新读取所有聊天。签名、真机、云账号
能力不由模型档位解决，验收卡必须先确认实际环境。

- D 核心上下文目标 ≤4k，C ≤6k，I ≤8k，R ≤12k；是调度建议，不是固定 token 预算。
- fresh fork 默认不带历史（`fork_turns: none`），只传有界卡片上下文。一次定向恢复仍失败时，不因低档 worker 不可用就默认升贵档；转给现有低档 worker 做机械工作，或保留状态等待可用性恢复。安全风险仍按 I/R 升级。
- 设计类工作做一次新边界设计冻结和一次最终 diff 审查；局部修复沿用同一 agent。机械账目、报告汇总不另开强 review；微小机械操作不单独增卡。
- 如一张卡仍需要多个候选、页面、runtime 或平台，再分 a/b 子卡；不要靠提高上下文上限
  吞并其他卡。顺序依赖遵从 execution policy 的 fresh-agent 要求；通过短事实摘要交接，不默认跨卡复用长历史。
- 不启动 Agent 或新聊天来“验证路由”；先用最近一批真实 ready 卡作为样本。

## 费用与质量记录

每张 task-result 记录实际型号/推理档位、input/output/cached/reasoning tokens（工具可得时）、
执行/评审/失败重试耗时、首次通过与否、发现缺陷、上下文是否越界及升级原因。
无法取得 token 数时填写 unavailable，不估作 0；订阅产品使用量和 API token 计价不是同一账单。

若使用 API：按执行时可核实的 input/cached/output 费率计算每次调用，再加评审/重试。
若价格数据不可得则只比较 token/耗时/质量，不伪造费用。更新定价只在校准时进行。
评价指标是“达到验收条件的总成本”，不是“第一轮调用最低价格”。

主聊天模型不能由这些工具自行切换；`spawn` 可指定新子 agent 模型，当前 `followup` 延续既有模型。主模型需由用户在 UI 更改。首批各取文档、fixture/规则、platform adapter、review 代表卡，比较同一验收；低档不能通过则
提高该类默认档位。只有确定通过且无质量退化才降档。无需为每卡同时运行三个模型，避免
为了省费用先花多倍评测成本。
