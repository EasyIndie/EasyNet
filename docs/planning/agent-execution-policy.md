## 分支、交付与最终合并

- 演进文档、PoC、测试和实现都提交到演进分支，不直接修改/提交 main。
- 每个小任务独立可审查 commit；不把长期演进做成单次大 commit。阶段 PR 若需要，只以
  演进分支为 base。可选短期工作分支也从演进分支派生并回到演进分支。
- G0/G1 等阶段验收不是 main 合并或正式生产发布授权。维护 main 修复可在演进分支吸收；
  记录冲突及定向回归，避免在共享长期分支强推改写历史。
- 测试产物标明 feature SHA 和非正式版本；不要打会触发现有正式 release job 的 semver tag。
  `tests.yml` 当前只监听 main PR/push 和 semver tags，需要单独任务为 feature PR/push 增加测试覆盖，
  并保持正式 release gate。测试 VPS 的 compat 与生产 balanced 约定继续适用。
- 在用户“全部演进完成”约束下，G0–G6 全部纳入最终合并检查，不再以只交付核心 G4 为合并门槛。
  可选 Agent、同步、原生 WG 等候选可以经明确 ADR 接受“不实施/不适用”，但不能用
  `verified` 冒充实现完成。取消/缩小已承诺范围需用户明确接受，不能自行把未完成项移出 gate。
- 最终才开向 main 的合并 PR：全任务状态与证据、平台支持范围、兼容迁移和回退文档、完整 CI/
  实客户端/实机验收、secret 扫描、最终 main 差异评审。获得最终合并授权后再合并。
  本规范不是提前授权 merge/deploy/云资源销毁。

## 模型分工与升级条件

默认执行任务使用用户选择的低成本模型；本规范不绑定某个厂商/型号或未核实的价格；[模型路由](model-routing.md) 提供
当前角色示例，具体分配以 [231 张任务卡](task-cards/README.md) 为准。
用户已明确授权按任务卡分配使用子 Agent。主 Agent 只派发 ready 卡，指定可用的模型与
推理档位；默认使用最小任务上下文，按依赖顺序执行并审核证据。研究/决策和跨模块审查
采用卡片的较强模型档位。无需逐卡重复请求模型授权；不自动生成数百个新聊天。
本授权不包括 main 合并、正式发布或未限定目标的云资源操作。

| 类型 | 低成本执行者可做 | 评审职责 |
|---|---|---|
| 文档/fixture/机械适配 | 给定文件与格式后的定向修改；只运行列出的检查 | 检查范围、状态和证据一致性 |
| 冻结合同后的代码 | 单一函数/adapter/数据验证规则、对应行为测试 | 抽查边界，阶段集成复核 |
| ADR/平台/Provider 选型 | 按固定表收集官方证据，单候选 PoC | 比较并接受决策；防止任务内隐式选型 |
| SSH trust/加密/权限/销毁/恢复 | 按已接受规范实现和生成故障测试 | 必须逐项审查，不能仅看测试绿 |
| Gate / 最终集成 | 执行已授权且明确的验收步骤，整理脱敏结果 | 确认真实环境及目标覆盖，判断阶段完成 |

以下任一情况停止扩大改动，输出 ≤10 行阻塞说明交给评审：接口/ADR 未定、需要读超过任务卡
列出的依赖、同一失败定向修复两次仍不通过、涉及信任/密钥/权限设计变更、跨越两个工作包、
改动超过文件或 diff 目标。先保存可审查 diff 和复现，不无限重试或反复发送整个仓库。
安全故障第一次发现即升级，不等两次。后续任务必须等前置状态 verified 或明确 accepted-not-applicable。

## 省 token 的工作方式

1. 读取短 AGENTS、任务卡和列出的局部代码；通用开发参考按变更领域读相关节。
   不为每个任务重新读取全部 roadmap、168 条目录、GitHub 历史或完整 CLAUDE 副本。
   后续卡默认派发新子 Agent（fork_turns=none）并给出有界输入；不要长期复用实现/
   评审 Agent 的逐卡聊天历史。只在同一卡局部修复时沿用其上下文。
2. 由准备者把下一批任务具体化：固定实现路径、接口版本、fixture、命令及预期结果。
   定位用 `rg`，先行号命中再小范围读取；未知工程目录先等语言 ADR，不猜路径。
3. 一卡一目标；读依赖的已接受合同即可，不复制全部上一轮聊天。
4. 默认只运行受影响测试。复用既有通过结果；阶段整合才跑完整相关套件。测试失败保存日志，
   返回失败摘要和必要片段，不回传几千行成功输出。
5. 最终输出 task ID、改动文件、测试结果、commit 或未提交 diff、残余限制；≤12 行为默认。
   每任务交接 ≤300 字；问题确需证据时不以字数为由隐藏信息。
6. 用状态台账去重；没有新增代码/故障/不确定性时不重复全量审计、浏览或实机验收。
   外部时变事实在需要选型/升级时核实，记录来源和日期，不每次刷新定价。

上述是上下文控制和减少返工的办法，不保证固定节省比例。可记录实际模型/token/任务耗时/
返工次数，再比较低成本执行 + 少量审查的总成本；不能只比较单次模型价格。

## 卡片解锁与完成状态

准备者从 [binding 模板](task-binding-template.json) 创建本卡 binding，冻结 implementation/test
文件、合同或证据版本、精确验证命令/预期、目标环境及实际授权；评审后 status=frozen。
同步卡 JSON 和 Markdown 的 allowed_writes、implementation_writes、锁条件和状态。
原实现输入尚不存在时，先由前置卡产出；不要用未来目录名称代替真实上下文。

验证：`python3 docs/planning/validate_task_cards.py --card <ID>`。
该命令只验证任务计划，不执行任何行为测试，也不把 locked 卡自动升级为 ready。
完成时增加 completion.evidence_path 和 completion.reviewed_by；不适用另需 ADR 路径。
实机/云/签名验收必须记录实际目标和报告；纯文档核对不能当作已通过系统验收。
